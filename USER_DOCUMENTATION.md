# CCTI User Documentation

## 1. Introduction

### 1.1 Purpose of the System

The Context-Specific Cyber Threat Intelligence (CCTI) platform is designed to collect, process, curate, and present threat intelligence that is relevant to specific organisational contexts.

The system uses CTI data from a MISP platform and processes it through a pipeline that reduces noise, extracts useful threat information, and generates organisation-specific recommendations. The goal is to help users focus on CTI that is more relevant to their industry, technology stack, and threat landscape.

The main goals of the platform are:

- Collect CTI from a MISP-based threat intelligence source.
- Reduce irrelevant or low-value CTI records.
- Process CTI into structured outputs.
- Match CTI against organisation profiles.
- Provide dashboard and API access to curated CTI outputs.

### 1.2 Intended Users

The CCTI platform is intended for:

- Security analysts who need to review relevant threat intelligence.
- Researchers studying CTI curation and recommendation methods.
- Organisations using MISP-based CTI workflows.
- Technical users responsible for maintaining CTI pipelines and dashboards.

### 1.3 Scope

This documentation covers:

- Accessing the CCTI dashboard.
- Understanding CTI ingestion from MISP.
- Viewing curated CTI outputs and recommendations.
- Understanding automated pipeline updates.
- Basic API usage.
- Deployment overview and troubleshooting.

This documentation does not cover detailed MISP administration or advanced model development.

## 2. System Overview

### 2.1 System Architecture

The CCTI platform is deployed as a server-based system using the following components:

- **MISP server**: Provides CTI data through the MISP API.
- **CTI pipeline**: Fetches, filters, processes, and transforms CTI data.
- **API service**: Serves processed CTI data to the dashboard and external clients.
- **Dashboard**: Provides browser-based access to curated CTI outputs.
- **Docker deployment**: Runs the CCTI pipeline and API as containerised services.
- **Apache reverse proxy**: Provides HTTPS access through the public domain.

The production deployment uses:

- MISP URL: `https://misp.cti-lab.me`
- CCTI URL: `https://ccti.cti-lab.me`
- Hosting platform: DigitalOcean Droplet
- Operating system: Ubuntu Server

### 2.2 Main Features

The main features of the CCTI platform are:

- CTI feed collection from MISP.
- Automated CTI processing through a pipeline.
- Noise reduction and filtering.
- Named entity extraction from CTI descriptions.
- STIX output generation.
- Context-specific recommendation generation.
- Dashboard access for reviewing CTI outputs.
- API endpoints for system health, CTI data, and recommendations.
- Automated updates using scheduled pipeline execution.

## 4. Dashboard User Guide

### 4.1 Dashboard Overview

The dashboard provides a browser-based interface for viewing processed CTI data and recommendation outputs. It is supported by the FastAPI backend service running inside the CCTI API container.

The dashboard displays:

- NER-enriched CTI records loaded from the latest pipeline cache.
- Filtered attribute count from the noise-reduction stage.
- Severity counts for critical, high, medium, and low records.
- Top CTI categories.
- Threat actor and malware entity lists extracted by the NER pipeline.
- A paginated raw intelligence table.
- Organisation-specific recommendation cards.
- Pipeline status stages: Fetch, Filter, Format, NER, Normalise, STIX, Recommend, Evaluate, and Vector DB.

### 4.2 CTI Event Display

Users can view CTI events that have been processed by the CCTI pipeline. The raw intelligence table displays:

- Threat category.
- Attribute type.
- Indicator or attribute value.
- Event information.
- Derived severity.

The dashboard reads CTI records from the latest successful pipeline output.

### 4.3 Recommendation Section

Recommendations are generated by matching processed CTI data against organisation profiles. These profiles describe organisational context such as:

- Industry sector.
- Technology stack.
- Known threat landscape.
- Relevant MITRE ATT&CK techniques.
- CPE-based technology identifiers.

The recommendation engine scores CTI events using a combination of textual similarity, asset matching, MITRE technique overlap, and severity weighting.

Higher-ranked recommendations indicate CTI items that are more relevant to a particular organisation profile.

### 4.4 Statistics and Visualisations

The dashboard provides statistics and visual summaries including:

- Number of CTI events processed.
- Threat category counts.
- Extracted entity counts.
- Severity counts.
- Recommendation scores per organisation profile.
- Score breakdowns for cosine similarity, CPE asset matching, MITRE technique overlap, and severity weighting.

If dashboard data appears outdated, verify that the pipeline has run successfully.

## 5. CTI Pipeline

### 5.1 Pipeline Workflow

The Docker pipeline is implemented in `pipeline.py` and performs the following steps:

1. Fetch CTI events from the MISP API.
2. Filter and clean noisy CTI data.
3. Prepare cleaned data for NER processing.
4. Extract CTI-related entities.
5. Normalise MITRE ATT&CK techniques.
6. Generate STIX 2.1 output.
7. Generate organisation-specific recommendations.
8. Evaluate recommendation outputs.
9. Ingest processed data into the ChromaDB vector store.

The pipeline is executed using Docker Compose:

```bash
docker compose --profile jobs run --rm pipeline
```

### 5.2 Automated Pipeline Updates

The deployed system uses cron to run the pipeline automatically. The standard schedule runs every 6 hours:

```cron
0 */6 * * * cd /opt/CCTI && docker compose --profile jobs run --rm pipeline >> /var/log/ccti-pipeline.log 2>&1 && docker compose restart api
```

This schedule:

- Runs the CTI pipeline.
- Saves logs to `/var/log/ccti-pipeline.log`.
- Restarts the API container so the dashboard serves the latest generated data.

### 5.3 Output Files

The pipeline generates several output files and folders:

- `data/misp/misp_raw_events.json`: Raw CTI data fetched from MISP.
- `data/cleaned/`: Cleaned and filtered CTI data.
- `ner/cti_ner_input.json`: NER-ready input data.
- `ner/ner_results_v3.json`: Extracted entity results.
- `ner/ner_results_v3_normalised.json`: Normalised NER output.
- `cti_microservice_v1/curated_threats_stix3.json`: STIX 2.1 output.
- `data/recommendations/`: Organisation-specific recommendation outputs.
- `cti_microservice_v1/vector_store/`: ChromaDB vector store output.

Generated output files are runtime artefacts. Rerunning the pipeline regenerates these files.

## 7. Deployment Overview

### 7.1 Hosting Environment

The CCTI platform is hosted on a DigitalOcean Droplet running Ubuntu Server.

The deployment includes:

- Ubuntu server.
- Docker.
- Docker Compose.
- Apache web server.
- HTTPS certificate.
- CCTI source code in `/opt/CCTI`.
- Host-installed MISP under `/var/www/MISP`.
- MariaDB, Redis, and Supervisor for the MISP service.

MISP and CCTI are deployed as separate services on the same cloud server. MISP is the upstream CTI platform, while CCTI connects to MISP through the REST API. CCTI does not directly access the MISP database.

The production layout is:

```text
https://misp.cti-lab.me
  -> Apache HTTPS virtual host
  -> host-installed MISP service

https://ccti.cti-lab.me
  -> Apache HTTPS reverse proxy
  -> http://127.0.0.1:8000
  -> Docker container: ccti-api-1
```

In this deployment, MISP is a host-installed service managed by Apache/PHP, MariaDB, Redis, and Supervisor. CCTI is deployed separately from `/opt/CCTI` using Docker Compose. This keeps the CTI source platform and the recommendation dashboard independent while allowing CCTI to fetch live data from MISP over HTTPS.

### 7.2 Docker Deployment

The Docker Compose deployment defines two main services:

- `api`: Runs the CCTI dashboard/API service.
- `pipeline`: Runs the CTI processing pipeline as an on-demand job.

Build the containers:

```bash
cd /opt/CCTI
docker compose build
```

Run the pipeline:

```bash
docker compose --profile jobs run --rm pipeline
```

Start the API:

```bash
docker compose up -d api
```

By default, this starts the full API module (`cti_microservice_v1.api:app`). To run the lightweight dashboard-only service instead, set `APP_MODULE=cti_microservice_v1.dashboard_only:app` in the environment before starting the container.

Check service status:

```bash
docker compose ps
```

View API logs:

```bash
docker compose logs -f api
```

The deployment script can be used to run the standard cloud deployment workflow:

```bash
cd /opt/CCTI
./deploy.sh
```

The script checks the environment, backs up `.env` and generated runtime data, pulls the latest code when enabled, rebuilds the Docker image, runs the pipeline job, starts the API service, and checks the health endpoint.

Useful deployment options include:

```bash
SKIP_PIPELINE=1 ./deploy.sh              # restart API without rerunning the pipeline
PIPELINE_ARGS="--use-secbert" ./deploy.sh # enable optional SecBERT extraction
BRANCH=main ./deploy.sh                  # deploy a specific branch
DEPLOY_ALLOW_DIRTY=1 ./deploy.sh          # deploy even when local generated files are modified
```

### 7.3 Reverse Proxy and HTTPS

Apache is used as a reverse proxy in front of the CCTI API container.

The public HTTPS URL is:

```text
https://ccti.cti-lab.me
```

Apache forwards public HTTPS traffic to the local CCTI API service running on:

```text
http://127.0.0.1:8000
```

This avoids exposing the raw Docker port directly to the internet and provides encrypted HTTPS access for users.

The MISP domain is also served by Apache with a separate HTTPS virtual host:

```text
https://misp.cti-lab.me
```

CCTI retrieves data from this MISP instance using:

```text
MISP_BASE_URL=https://misp.cti-lab.me
MISP_API_KEY=<configured in .env>
MISP_EVENT_LIMIT=200
```

The API key should be created in MISP from the administration authentication key page and then stored only in the server `.env` file. Do not commit real MISP keys, Groq keys, encryption keys, passwords, or private certificates to the repository.

### 7.4 Automated Cloud Updates

The cloud server can update CTI data automatically using cron. The current deployment pattern is:

```cron
0 */6 * * * cd /opt/CCTI && docker compose --profile jobs run --rm pipeline >> /var/log/ccti-pipeline.log 2>&1 && docker compose restart api
```

This scheduled job runs the pipeline, writes the pipeline log to `/var/log/ccti-pipeline.log`, and restarts the API container so the dashboard loads the latest generated files.

### 7.5 Server Migration

To move CCTI to another server or restore it locally:

1. Clone the repository on the target machine.
2. Copy `.env.example` to `.env` and set the required values again. Do not commit `.env`.
3. Configure the new server to reach the MISP API. This can be the existing cloud MISP instance or a new local/cloud MISP instance.
4. If reusing generated demo data, copy these runtime paths from the old server:
   - `data/misp/`
   - `data/cleaned/`
   - `data/recommendations/`
   - `ner/ner_results_v3.json`
   - `ner/ner_results_v3_normalised.json`
   - `cti_microservice_v1/curated_threats_stix3.json`
   - `cti_microservice_v1/vector_store/`
5. If encrypted runtime files are reused, copy the same `CCTI_ENCRYPTION_KEY` into the new `.env`.
6. Rebuild and start the API:
   ```bash
   docker compose build
   docker compose up -d api
   ```
7. If generated data is not copied, run a fresh pipeline:
   ```bash
   ./deploy.sh
   ```

For a cloud migration, also update DNS records, Apache virtual host settings, HTTPS certificates, firewall rules, and any external MISP or Groq API keys tied to the previous host.

## 8. Troubleshooting

| Issue | Resolution |
| --- | --- |
| API unavailable | Restart the API container with `docker compose up -d api`. |
| Pipeline failed | Check MISP connectivity and verify `MISP_BASE_URL` and `MISP_API_KEY` in `.env`. |
| No dashboard data | Run the pipeline and restart the API container. |
| HTTPS issue | Check DNS propagation, Apache configuration, and certificate status. |
| Docker command fails | Verify Docker is installed and the Docker service is running. |
| MISP API connection fails | Test the MISP URL from the server and confirm the API key has permission. |
| Out-of-memory errors | Reduce `MISP_EVENT_LIMIT`, add swap, or resize the Droplet. |

Useful commands:

```bash
cd /opt/CCTI
docker compose ps
docker compose logs --tail=100 api
docker compose --profile jobs run --rm pipeline
curl http://localhost:8000/api/v1/health
tail -f /var/log/ccti-pipeline.log
```
